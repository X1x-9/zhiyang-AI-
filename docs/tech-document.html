01

项目概述

1.1 背景与定位

智养AI 的设计出发点是把生活方式指导做得低门槛、可持续、不越界：不走医疗诊断路线，也不走指标堆叠路线，而是定位为面向普通用户的综合型 AI 健康管理平台，覆盖饮食、运动、体重、复盘与健康助手五大板块，微运动只是运动板块中的一个模块，而非产品全部。

平台以三条原则贯穿全部设计：诚实——缺数据不猜测、示例必标注、计划修订只描述真实变化；可解释——指南建议带引用回链，AI 工具调用顺序落日志可审计；有边界——不诊断、不开处方、不承诺疗效，输入与输出两端都有安全校验。项目作为传智杯参赛项目，以 AI 技术深度为核心建设方向。

1.2 目标用户与使用场景

健身初学者不知道练什么、练多久，难以坚持按器械与时长排训练；逐项打卡；周复盘同步完成度
学生与备考人群时间碎片化，需要轻量记录与鼓励式陪伴健康搭子多轮对话与语音播报；轻提示与今日切片概览
评审与演示观众需要在无真实数据时完整体验闭环演示沙盒按会话隔离，真实账号与演示数据互不污染

2.3 边界与约束

  • 非医疗器械边界：所有输出止于生活方式层面，禁止诊断、治疗、药物与疗效保证；紧急情形绕过模型直接应急回复。
  • 数据诚实边界：趋势与统计只来自真实记录或授权采集；未记录餐食不等于没吃，建议重点只由汇总信号触发，不凭单日记录推断。
  • 运行约束：密钥经环境/终端注入；演示与真实身份按会话沙盒隔离，dev/预览/公网三环境端口分离（3.6）；未经明确要求不构建、不发布。
  • 交付约束：技术文档 PDF 不超过 30 页，须覆盖概述、需求、架构、AI 方案、实现、测试部署、总结展望，并单列创新点。

系统架构设计

3.1 总体架构

平台采用 Next.js 16 App Router 全栈单体：客户端 React 19 组件经 API Routes 调用服务层 lib/*，服务层统一访问 MySQL 8 与外部 AI/数据服务。AI 能力不分散在页面里，而是收敛为「安全闸门 → 模型路由 → 工具/RAG → 输出校验 → 日志」一条可审计链路。

图 3-1 总体架构：客户端 → API Routes → 服务层 → 数据与外部服务

以助手请求为例：身份解析与限流 → 输入安全闸门 → MCP 工具（安全核对/知识检索/营养/天气）→ 流式生成 → 句级输出校验 → SSE 推送，同时整条链路写入 .ai-logs。计划请求则先经确定性引擎计算，再由受约束 Agent 补充建议，两者产物合并为新的 PlanVersion。

3.4 身份体系与演示沙盒

正式身份基于 next-auth（邮箱+密码，bcryptjs 哈希），resolveIdentity 统一解析「真实用户 / 演示会话」两种身份；所有业务读写按身份归属隔离。演示模式开启时向访客下发 httpOnly cookie（zy_demo_session，UUID），服务端按 sessionId 开辟内存会话沙盒：资料、餐食、体重、训练各用独立 Map 存放，不写真实 MySQL 表，服务重启即自然清空；不同演示会话互不可见，也不污染真实账号。DEMO_MODE 是环境级开关（true 强制开 / false 强制关），与会话级隔离正交：开关决定「是否提供演示身份」，沙盒决定「演示数据如何隔离」。接口层叠加 rateLimit(clientKey(...)) 按用户/IP 限流；生产清单要求正式环境置 DEMO_MODE=false、API 默认拒绝以演示 ID 代替鉴权（见 docs/production-readiness.md），公网 ECS 按此配置、默认真实身份。

3.5 前端架构

  • 状态分层：服务端数据走 TanStack Query（缓存/失效/乐观更新），客户端瞬时状态走 Zustand，避免竞争状态源。
  • 设计系统：手写 CSS 按页面拆分，白瓷 + 鼠尾草绿主色、琥珀强调；乐米小语品牌字标；图标 lucide + 品牌 Mochi 头像。
  • 动效与无障碍：Framer Motion 入场/悬停/翻面动效，全部在 prefers-reduced-motion 下降级；焦点可见、提示可再次唤出。
  • 体验保活：页面保活与滚动记忆、聊天固定高度内部滚动、移动端输入框避开底部导航；三档视口回归。

04

AI 技术方案

4.1 AI 能力总览与选型理由

能力当前部署选型选型理由
对话助手deepseek-flash · 关思考陪伴式对话要求低延迟与稳定工具调用；思考 token 是该场景主要延迟源，关闭后端到端秒级
计划 Agentdeepseek-v4-pro · 开思考 + reasoning_effort多约束推理（营养/器械/天气/忌口）需要深度；生成是低频异步操作，可容忍数十秒
餐食视觉qwen3.8-flash 看图 + deepseek-v4.1-flash 出 JSON视觉与结构化解耦：看图模型负责食材/份量，JSON 模型负责 zod 约束输出，各自可独立替换
嵌入text-embedding-v4 · 1024 维中文语义质量优；docs/rag-guide.md 预留同维 Ollama bge-m3 本地离线路径（文档化备选，当前部署未启用）
向量存储MySQL JSON 列 + 应用层余弦复用既有数据库、零新增运维；62 片段规模下平均 23ms；万篇级有明确向量索引迁移路径
工具协议MCP（server + client + /api/mcp）标准协议、工具可独立冒烟测试；助手与外部集成共用同一链路
天气Open-Meteo免密钥、实时预报；失败显式返回 UNAVAILABLE，机制上禁止编造天气
语音Web Speech API浏览器原生、零后端成本；识别入框可编辑、播报逐条可停止

所有模型经 AI SDK 统一抽象（streamText / generateText / tools / stopWhen），provider 按场景分离：对话、计划、视觉、餐食、嵌入各有独立凭证与 base URL 配置，互不牵连，可单独降级或替换。表中模型名为网关配置层的路由别名：DeepSeek 系列承担对话/计划/结构化输出，Qwen 系列承担视觉，DashScope 提供嵌入；具体厂商版本号随网关配置，代码只依赖 provider 抽象，改配置即可整体替换而不改业务代码。

术语约定：MCP（Model Context Protocol）模型调用外部工具的标准化协议；BM25 经典概率关键词检索算法；Hit@K 前 K 条检索结果是否包含期望片段；MRR（Mean Reciprocal Rank）首个正确结果排名倒数的均值；SSE（Server-Sent Events）服务端单向流式推送；reasoning_effort 推理力度参数，控制模型思考深度。

4.2 模型路由与流式集成

思考开关在 fetch 包装层注入：withThinking("disabled") 为对话关闭思考，withThinking("enabled", effort) 为计划开启并附 reasoning_effort；餐食链路注入 enable_thinking:false。开关全部由环境变量驱动（CHAT_DISABLE_THINKING / PLAN_ENABLE_THINKING / MEAL_DISABLE_THINKING），不改代码即可做延迟/深度权衡。

图 4-1 流式对话管线：输入闸门 → 工具增强生成 → 句级缓冲 → 后置校验 → SSE

缓冲器只在句子边界（。！？；换行）切分，完整句子才进入校验，因此首句延迟不被安全校验拖慢，也不会把半句话误判。流结束时 flush 剩余文本、按需追加免责声明与来源 footer，并调用 logger.finish 记录 usage、finishReason 与 post_guard 标记。

4.3 受约束计划 Agent

计划数值与排程由确定性引擎完成；Agent（lib/plan-agent.ts）只读取依据、在边界内补充说明。上下文注入资料、营养目标、餐食信号与规则引擎已排好的训练安排；stepCountIs(8)、maxOutputTokens 1600、temperature 0.2 约束步数与发散。白名单工具中 applyFocus 仅在餐食汇总存在对应信号时才把「蛋白质重点 / 份量重点」写进食次建议，每次至多一项、不自动改热量目标；getWeatherForecast 无城市或服务失败时显式失败，禁止编造天气。

图 4-2 受约束 Agent 循环：白名单工具 → 校验（拒绝即记录并令模型自纠）→ 捕获 → 持久化

拒绝不是静默过滤：每次越界调用写入 toolLog REJECTED 并把原因返回模型令其自纠。真实日志可见 addCoachNote:REJECTED（非指南说明绑定引用、医疗越界等）后模型改写为合规说明（见 6.4）。Agent 产物随 PlanVersion 持久化，但界面不铺开解释面板——决策过程以日志佐证，对用户克制、对评审透明。

4.4 RAG 知识检索与引用回链

语料为 27 篇 / 62 片段：中国居民膳食指南、健康中国行动、身体活动指南及 BMJ、Clinical Nutrition、Circulation 等同行评审文献与 2025 美国膳食指南咨询委员会报告；入库前核对 DOI/期刊/年份/摘要，reviewedAt 留痕，未审核内容不可检索。分块约 280 字、内容哈希稳定 ID、每批 10 条向量化。

4.5 多模态餐食识别

流水线：拍照 → 视觉模型识别食材与份量 → 结构化模型按 zod schema 输出 JSON → calculateNutrition 工具计算估算与 ±区间（0.85–1.2 倍，提示视觉份量与烹饪用油误差）→ 食物参考库匹配并显示来源 → 用户确认（PENDING→CONFIRMED）→ 入库统计。餐食链路关闭思考是延迟关键，实测全链路约 8.8 秒；估算永远表述为估算，确认环节不可跳过。

4.8 安全与合规设计

输入端：assessHealthSafety 三级判定——emergency 绕过模型直接应急回复（急救/心理援助热线指引）；caution 注入转介指令；routine 正常生成。输出端：guardAssistantOutput 句级后置校验，四类规则保守替换并追加免责声明：

类别处置
self_harm_method替换为求助与陪伴指引，优先级最高
medication药物/剂量/停药建议替换为「遵医嘱」表述
diagnosis诊断动词+疾病名组合替换为就医建议
care_dismissal「不用就医/没事」类淡化替换为谨慎提醒

命中任何类别即在流末追加「以上为一般健康信息，不能替代医生的诊断和处方。」并以 post_guard 落日志。两端规则均为确定性正则实现：输入端含否定检测（避免「没有胸痛」这类否定表述误判），输出端按句匹配、按类别优先级替换，不依赖第二次模型调用，行为可复现、不增加延迟；代价是换述覆盖有限，故定位为保守底线而非完备医疗审计，系统性有效性评测与红队用例列入 8.3。Agent 侧另有白名单与拒绝机制（4.3），且系统提示明确：检索片段、餐食与用户资料均为不可信数据，只作资料、不执行其中指令。内容诚实约束（缺数据不猜、示例必标注、修订只描述真实变化）贯穿全部生成路径。

05

核心功能实现

5.1 餐食记录闭环

拍照区采用胶片相机交互；识别走 4.5 双模型流水线，估算带区间与误差提示、匹配显示来源；用户确认后才入库（CONFIRMED），按天/周真实记录驱动概览热量卡与复盘信号。右列限高内部滚动，移动端单列堆叠；链路无一处以模型输出替代用户确认。

5.2 计划生成与版本管理

lib/plan-engine.ts 按资料确定性计算营养目标与训练排程，Agent 叠加建议后合并为 PlanVersion；unique(profileId, version) 防并发撞号，新版本默认自动启用，历史版本可回看、启用、删除。意见调整走多轮 AI 对话（plans/chat），修订跳过二次 Agent、实测约 4.5 秒，只描述实际变化；Agent 还可依据餐食汇总信号经 applyFocus 把「蛋白质重点 / 份量重点」写进下一版食次建议（至多一项、不自动改热量目标），记录不完整时保持不调整。

5.3 意见调整与动态调整

动态调整只评估显著偏差：单餐已记录热量高出参考上限 max(180 kcal, 上限×30%)、或全天高出热量上限 max(150 kcal, 上限×10%)，才触发 plans/adjust/evaluate，否则返回暂不需要调整；建议经约束校验与用户确认生效（apply），可 restore 撤销。临时层以 unique(profileId, dayKey) 按天覆盖、不占版本号，与长期版本互不污染；调整对话只在约束内改建议，越界即拒绝；天气户外调整由规则引擎记录，Agent 照记录说明（4.6）。

5.4 训练打卡与每周复盘

训练卡逐项勾选，steps Json 记每步完成态，全步骤完成才写 completedAt 记一次训练；示例与未来日期不可打卡。周复盘同步完成记录，与餐食偏差信号构成调整输入；训练日可指定，器械多选筛选动作。

5.5 体重与数据趋势

体重同日覆盖（unique(profileId, dateKey)），我的空间填写只读同步概览/复盘；资料体重作标注来源的趋势起点，单条即出图、同值也显示，平线用局部刻度防误导；趋势只认真实记录，无记录不画图、不虚构。

5.6 健康搭子对话与语音

多会话按账号隔离，固定高度内部滚动 + 全屏；手机输入框避开底部导航、首屏可见。语音经 Web Speech 入框可编辑再发送，播报逐条可停；来源栏引用回链（4.4），回答禁 Markdown 与工具过程说明，点赞/点踩留痕 Feedback 表。浮动头像可拖拽（拖动≠点击），气泡悬停/聚焦可再唤出且不出屏。

5.7 概览页与今日训练

今日训练卡只读已启用计划三态（训练 / 休息 / 未启用），开始训练跳转计划页；饮水柱状图按天持久化；今日切片九宫格可点击跳转，悬停凸起、其余模糊，减弱动效全降级。

06

测试与部署

6.1 质量门禁

每次改动执行 npm run typecheck（tsc --noEmit）与 npm run lint，基线保持 0 error（5 条 img 警告为已接受的 Next 图片提示）。项目无单元测试框架，行为正确性由「检索评测脚本 + 三端浏览器回归 + 端到端彩排」三层验证承担，所有验收在本地 dev 完成，未经明确指令不构建、不发布。

6.2 检索评测

评测集 content/rag-eval.json 与语料同步构建：39 条正向题按知识库文档标题逐条写成口语化换述，expectTitle 标注期望命中文档（须与标题完全一致）；4 条负向题为天气/代码/电影/路由器等域外请求，期望 NO_MATCH。npm run rag:eval 调用 /api/rag/eval，对 43 条逐条跑 hybrid / vector / keyword 三策略，输出 Hit@3、Hit@5、MRR、负向通过率与平均耗时，并列出未命中与负向误召回明细；报告写入 .rag-eval/last-report.json 供复核。最近一次（2026-11-12）hybrid 全指标 100% / MRR 0.987 / 23ms，未命中与误召回均为 0（4.4）。评测集与语料同步扩充，形成「改检索→跑评测→看明细」的闭环。

6.3 浏览器回归与演示彩排

回归采用 headless Chrome + CDP、仅访问 localhost，覆盖 1440 桌面、1415×949 与 390 移动三档视口；计划弹窗等重交互可用 mock profile/plan 隔离验收。端到端彩排走完整链路：注册→建档→拍照记餐→生成计划→意见调整→打卡→复盘→助手对话→体重记录，真实账号与演示沙盒各跑一遍；演示 QA 以 DEMO_MODE=true 重启 dev 跑演示链路后复原——开关是环境级、沙盒隔离是会话级（3.4），两者正交，保证真实与演示两种身份互不串流。

6.4 请求日志佐证

.ai-logs 只记录元数据与字符数（textChars），不落敏感提示词全文，兼顾审计与隐私。4.9 的两条记录分别佐证：对话工具顺序「先安全核对、后知识检索」且 post_guard=clean；计划 Agent「先读依据→天气失败不编造→越界说明 REJECTED 后自纠→rag=OK」。写提交材料时直接引用 toolSequence / agent_tools / post_guard / latencyMs 字段即可复核，无需在界面展示决策面板。

6.5 部署与运维

公网部署于阿里云 ECS：Node 24 + MySQL 8，prisma generate && next build 后以 systemd 服务常驻，环境变量注入 AUTH_SECRET / DATABASE_URL / 模型密钥，密钥不入源码、不入仓库。迁移与运行时凭证分离，运行时角色仅授所需表权限。本地 dev（3100）/ 生产预览（3102）/ 公网 ECS 三环境解耦：本地验收通过后才按明确指令更新公网；计划版本历史与 git 快照提供行为级与代码级双重回退。公网当前为 HTTP 直连（未配域名与 HTTPS），备份与监控的现状和补齐计划见 8.2 / 8.3。

07

创新点说明

7.1 技术创新点

  1. 确定性引擎 + 受约束 Agent 的两段式决策。营养计算、目标与排程全部由规则引擎完成；Agent 只能通过白名单工具读取依据、在边界内补充建议，越界调用被拒绝并记录原因。决策过程持久化为 toolLog 并汇入 .ai-logs 的 toolSequence/agent_tools 字段，形成可审计证据链（见 4.3、6.4）。
  2. 混合检索 + 重排 + 引用回链 + 评测闭环。向量 ∪ BM25 双路互补召回、归一化重排，向量不可用时关键词独立降级；答案引用绑定具体指南序号并可回链；配套 43 条含负例的评测集，Hit@3 / Hit@5 100%、MRR 0.987，并如实报告当前评测集上 vector 单路与 hybrid 持平、增量在互补与降级稳健性（见 4.4、6.2）。
  3. 流式句级输出后置安全校验。在 SSE 流上按句子边界缓冲，命中医疗越界规则的句子被保守替换并追加免责声明，不牺牲首句延迟；校验结果以 post_guard 标记落日志（见 4.8）。
  4. MCP 标准化工具集成。自建 MCP server 暴露 4 个工具并经 /api/mcp 提供，助手以真实 MCP Client 调用，天气等外部数据走同一协议链路，工具可独立冒烟测试（见 4.6）。
  5. 双模型场景路由与思考开关。对话用 flash 关思考保低延迟，计划用 pro 开思考保推理深度，餐食用视觉 + JSON 双模型分工；按场景配置 temperature / token 上限 / 步数上限（见 4.2、4.7）。
  6. 天气→确定性调整→Agent 说明的两段式诚实设计。户外训练调整先由规则引擎按实时预报完成并记录，Agent 只照记录说明，从机制上杜绝模型虚构「改过训练」（见 4.6、5.3）。

7.2 应用创新点

  1. 「缺数据不猜」的诚实健康管理。把内容诚实做成产品级约束：无资料不展示示例计划、不虚构健康分与疾病风险、示例必标注、计划修订只描述真实变化——把「不编造」当成产品约束而非宣传话术。
  2. 版本 / 临时层 / 实时层三层计划分离。长期目标走版本管理，短期波动走不占版本号的临时动态层，天气走确定性实时调整；三者互不污染，用户可随时回看与启用历史版本。
  3. 真实账号与演示沙盒双轨。评审无需注册即可按会话隔离体验完整闭环，演示数据与真实数据互不串流，兼顾比赛演示与真实可用。
  4. 低刺激陪伴感与无障碍一体设计。白瓷 + 鼠尾草绿的低刺激视觉系统与品牌字标降低焦虑感；正文对比度 12.3:1、减弱动效全降级、可再次唤出的提示、三档响应式回归，把「陪伴感」与「可访问性」用可测指标同时落地（NFR-05）。
  5. 证据链式交付。AI 决策过程不在界面铺开解释面板，而是后台持久化、日志佐证，提交材料直接引用字段——对用户克制、对评审透明。
08

总结与展望

8.1 总结

智养AI 完成了「记录→计划→执行→复盘→调整」的真实闭环，并围绕 AI 技术深度建成六项能力：受约束 Agent、混合检索引用、流式后置安全、MCP 集成、双模型路由与天气联动。质量门禁保持类型检查与 lint 0 error，检索评测全指标达标，公网部署可用，全部关键行为均有源码与日志佐证。项目证明了「有边界的 AI」可以在消费级健康场景中同时做到有用、可信、可审计。

8.2 局限

  • 模态覆盖：已覆盖图像、文本、语音，视频模态（如动作视频分析）尚未实现。
  • 评测规模：43 条检索评测集覆盖主要指南主题，但规模有限，需持续扩充与线上监控。
  • 检索扩展性：向量存于 MySQL JSON 列、应用层计算相似度，千篇级知识库足够，万篇级需引入向量索引。
  • 语音依赖：Web Speech 识别与播报依赖浏览器实现，跨浏览器体验不一致。
  • 计划延迟：开思考的计划 Agent 单次生成约数十秒，需靠异步反馈与日志持续优化。
  • 运维与安全评测：公网当前 HTTP 直连（未配域名与 HTTPS），备份与监控依赖人工与 systemd 自动重启；双端安全规则仅有冒烟级 post_guard 记录，缺系统性红队有效性评测。

8.3 展望

  • 引入视频模态：训练动作短视频的要点提示与计数，补齐多模态最后一块。
  • 检索升级：扩充评测集至数百条、引入向量索引与在线命中率监控，保持评测驱动迭代。
  • 长期记忆：在隐私边界内沉淀用户长期偏好与历史响应，让计划随时间更贴合本人。
